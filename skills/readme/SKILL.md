# readme: 처음 온 사람이 30초에 판단하게

README를 잘 썼는지는 작성자가 판단하지 못한다. 이미 다 알기 때문이다.
그래서 맥락 없는 haiku 서브에이전트에게 읽히고, 답을 못 하는 자리를 고친다.
haiku는 여기서 글을 쓰는 게 아니라 처음 온 사람 노릇을 한다.

## 구조

| 절 | 담는 것 |
|---|---|
| 제목 아래 | 한 줄 정의와 어떤 상태면 성공인지. 들어 있는 것은 항목으로 |
| 설치 | 복붙 가능한 명령. 전제조건과 설치 후 동작은 명령 아래 항목으로 |
| 사용 | 가장 흔한 사용 하나. 여럿이면 표 |
| 구성 | 이 리포의 파일과 역할 |
| 외부 의존 | 남의 패키지. 라이선스와 받는 곳을 표로 |
| 제거 | 설치가 건드린 것을 되돌리는 법 |
| 수정 | 원본이 어디인지, 고친 뒤 무엇을 하는지 |

- 없는 절은 넣지 않는다. 외부 의존이 없으면 그 절도 없다
- 산문은 첫 줄 정의와 절 도입부에만 쓴다. 나머지는 개조식
- 표 셀은 40자 안에 끝낸다. 넘으면 화면에서 줄이 어색하게 감긴다
- 셀에 하는 일과 왜 좋은지를 같이 넣지 않는다. 뒤쪽은 그 스킬 문서에 이미 있다
- 60줄이 넘으면 docs/로 뺀다

## 절차

1. 리포를 읽는다. 진입점, 설치 스크립트, 실행 명령, 디렉토리 구조, 의존 패키지
2. README가 이미 있으면 갱신 모드다. 새로 쓰지 않고 실제 상태와 어긋난 곳만 고친다
3. 위 구조로 쓴다. 리포에 이미 문서 규약이 있으면 그것을 따른다
4. 적힌 명령을 실제로 돌린다. 설치는 가짜 HOME으로, 제거는 그 설치본에 대고 돌린다.
   안 되는 명령이 적힌 README가 제일 나쁘다
5. 신입 테스트. Agent 도구를 model "haiku"로 불러 아래 템플릿에 README 본문만 넣는다.
   Agent 도구가 없는 환경이면 `claude -p "<프롬프트>" --model haiku` 헤드리스 호출로 대신한다.
6. 못 답한 항목을 보강하고 5번을 한 번 더 돌린다.
   4번 목록이 별 개수나 벤치마크처럼 리포가 사실로 댈 수 없는 것만 남으면 거기서 멈춘다.
   없는 사실을 지어내 채우지 않는다
7. 어휘를 훑는다. 전역 규칙의 금지 기호와 금지 단어를 확인한다.
   한국어 문체가 걸리면 humanize-korean 스킬을 태운다. 다만 그 스킬은 문장 구조만 보고
   어휘 선택은 보지 않으니, 딱딱한 단어는 직접 잡는다

## haiku 프롬프트 템플릿

```
아래는 어떤 GitHub 리포의 README 전문이다. 너는 이 리포를 처음 보는 사람이다.
README에 적힌 내용만 근거로 세 질문에 답하라. 없는 내용은 "README에 없음"이라고 답하라.
도구를 쓰지 말고 즉시 답하라.

1. 이 프로젝트는 무엇을 하는 물건인가. 한 문장으로
2. 어떻게 설치하나. 실행할 명령을 그대로 적어라
3. 이 README만 보고 설치할지 판단할 수 있나. 첫 줄에 "판단 가능" 또는 "판단 불가"만 적어라
4. 판단에 필요한데 없는 정보를 나열하라

마지막에 "막힌 지점:" 항목으로 읽다가 걸린 곳을 솔직하게 적어라. 없으면 "없음".

README 전문:
<README 본문>
```

## 합격 기준

1번과 2번을 정확히 답하고, 3번이 "판단 가능"이고, 막힌 지점이 없으면 합격이다.

## 실측으로 알게 된 것

- 진짜 버그는 4번 명령 검증에서 나온다. 문서를 읽어서는 안 보인다.
  npm 리포 시험에서 `npm install -g .` 만 적으면 실행이 죽는 것을 여기서 잡았다
- haiku는 4번에서 늘 무언가를 더 요구한다. 별 개수, 벤치마크, 유지보수 계획 같은 것이다.
  그래서 6번에 멈추는 조건을 둔다. 요구를 다 채우려 들면 없는 사실을 짓게 된다
