# release: 읽는 사람은 올릴지 말지를 정한다

릴리스 노트는 설명서가 아니다. 이번 판으로 올릴지, 올리면 무엇이 깨지는지를 정하게 하는 글이다.
그래서 깨지는 변경이 맨 위에 오고, 나머지가 그 아래에 온다.
커밋 로그를 그대로 붙이지 않는다. 사용자가 겪는 변화로 다시 쓴다.

## 형식

```
## 깨지는 변경
- 무엇이 어떻게 달라졌는지 한 줄
  이전: <코드나 설정>
  이후: <코드나 설정>

## 새 기능
## 고침
## 그 외
```

- 리포에 이전 릴리스가 있으면 그 형식과 언어를 그대로 따른다. 새 형식을 덮어씌우지 않는다
- CHANGELOG.md가 있으면 그 분류 이름을 쓴다
- 둘 다 없으면 위 형식을 쓴다. 버전 체계가 불분명하면 사용자에게 묻는다
- 빈 절은 통째로 뺀다. 깨지는 변경이 없으면 그 절도 없다
- 항목은 한 줄. 사용자가 겪는 변화를 쓴다. 파일명, 함수명, 커밋 해시는 쓰지 않는다
- 깨지는 변경만 이전과 이후를 나란히 보인다. 이게 이 문서의 값이다
- 새 기능은 부르는 형태를 한 줄 보인다. 있다는 사실만으로는 쓸 수 없다

## 버전 고르기

semver는 MAJOR.MINOR.PATCH다. 세 자리가 각각 무엇이 바뀌었는지를 말한다.

| 자리 | 올리는 때 |
|---|---|
| MAJOR | 쓰던 코드가 깨진다 |
| MINOR | 기능이 늘었고 기존 것은 그대로 돈다 |
| PATCH | 고치기만 했다 |

- 0.x대에서는 깨지는 변경도 MINOR로 올린다. 관례다
- 리포가 semver를 안 쓰면 그 리포의 방식을 따른다

## 절차

1. 범위를 정한다. `git describe --tags --abbrev=0`로 직전 태그를 찾고 거기부터 HEAD까지다.
   태그가 없으면 첫 커밋부터다
2. `git log <직전태그>..HEAD --format='%s%n%b%n---'`로 커밋을 읽는다.
   이전 릴리스 형식은 `gh release view --json body` 또는 GitHub MCP의 get_latest_release로 확인한다
3. 커밋을 절별로 나눈다. 깨지는 변경은 커밋 본문이 아니라 diff에서 확인한다.
   지운 함수, 바뀐 설정 키, 달라진 기본값, 달라진 반환 형태가 후보다.
   커밋 타입은 근거가 아니다. refactor와 perf와 fix도 공개 API를 건드리면 깨지는 변경이다
4. 버전을 정하고 초안을 쓴다
5. haiku 검증. Agent 도구를 model "haiku"로 불러 아래 템플릿에 초안만 넣는다.
   Agent 도구가 없는 환경이면 `claude -p "<프롬프트>" --model haiku` 헤드리스 호출로 대신한다
6. 못 답한 항목을 보강하고 5번을 한 번 더 돌린다
7. 발행 전에 버전 표기가 남은 곳을 맞춘다. package.json, pyproject.toml, Cargo.toml 같은 자리다
8. 발행한다. `gh release create <태그> --title <제목> --notes-file <파일>`.
   `gh`가 없으면 노트를 파일로 저장하고 그 경로와 명령을 사용자에게 보고한다.
   발행은 되돌리기 어려우니 초안을 먼저 보이고 확인을 받는다

## haiku 프롬프트 템플릿

```
아래는 어떤 프로젝트의 릴리스 노트다. 너는 이 프로젝트를 쓰고 있는 사용자다.
노트에 적힌 내용만 근거로 답하라. 도구를 쓰지 말고 즉시 답하라.

1. 이 버전으로 올리면 내 코드가 깨지나. 첫 줄에 "깨짐" 또는 "안 깨짐"만 적어라
2. 깨진다면 무엇을 고쳐야 하나. 노트에 적힌 대로 적어라
3. 이번 판에서 새로 생긴 것은 무엇인가

마지막에 "막힌 지점:" 항목으로 읽다가 걸린 곳을 적어라. 없으면 "없음".

릴리스 노트:
<초안>
```

## 합격 기준

1번에 판정이 나오고, 깨진다면 2번에 고칠 방법이 적혀 있고, 막힌 지점이 없으면 합격이다.
